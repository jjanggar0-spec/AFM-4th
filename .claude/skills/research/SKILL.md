# 리서치 → 보고서(.md) + 웹페이지(.html)

주제를 웹에서 직접 조사해 **근거(출처 링크)가 달린** 마크다운 보고서를 만들고, 같은 내용을 한 파일짜리 웹페이지로 만든다.

## 두 가지 모드

| 모드 | 언제 | 먼저 물을 것 | 파일 이름 · 위치 |
|---|---|---|---|
| **A. 지역 업체 모드** | 안과·병원·맛집 등 **지역 업체**를 조사할 때 | ① **Area** ② **부정 리뷰를 분석할 업체** (아래 1-A) | `{Area}(YYYY-MM-DD).md/.html` → `week-5/quest/Reserch/` |
| **B. 일반 모드** | 제품·기술·정책 등 그 밖의 주제 | 주제·키워드·범위 (아래 1-B) | `Research(YYYY-MM-DD).md/.html` → `week-N/quest/<주제-슬러그>/` |

## 워크플로

1. **먼저 묻기**: 조사를 시작하기 전에 반드시 사용자에게 묻는다. 답을 받기 전에는 탐색하지 않는다.
2. **브라우저 MCP로 3곳 이상 탐색**: Playwright로만 검색한다(CLAUDE.md 규칙). WebSearch/WebFetch로 대신하지 않는다.
   - A 모드는 검증된 수집 코드가 [references/naver-place-scripts.md](references/naver-place-scripts.md)에 있다. **먼저 읽고 그대로 쓴다.**
3. **`.md` 작성**: 수집한 사실, 출처, 한계를 쓴다. A 모드는 [references/area-report.md](references/area-report.md)의 분석 순서와 틀을 따른다.
4. **`.html` 작성**: 같은 파일명, 같은 폴더에 둔다. 브라우저로 열어 검증한 뒤 기본 브라우저로 띄운다.

## 1-A. 지역 업체 모드: Area와 대상 업체 묻기

요청에 업종(예: 안과)만 있고 Area나 대상 업체가 빠져 있으면 **AskUserQuestion** 으로 묻는다. 선택지를 주면 사용자가 빨리 답한다.

- 질문 1, **Area**: 시·구 단위 / 동 단위 / **특정 업체 기준 반경 N km**. 직전 리서치 지역을 추천 선택지로 둔다. 반경이면 기준 업체 이름을 '기타'에 받는다.
- 질문 2, **부정 리뷰를 분석할 업체**: 특정 업체 지정 / Area 안 리뷰 많은 상위 N곳.
- 선택 사항(답이 없으면 기본값): 키워드(기본: 후기 전반).

- 사용자가 준 업체 이름이 네이버에서 안 나오면 비슷한 이름(띄어쓰기, `의원` 붙이기, 오타)으로 찾아본다. 예: "연세항정외과" → "연세항정외과의원".
- 대상이 안과가 아니면 대상 업체의 **진료 분야**를 확인해서 Area 비교 업종을 정한다. 예: 항문외과 → 외과·대장항문과. 같은 업종 안에서도 리뷰 내용으로 분야(항문/정맥/유방 등)를 나눠 직접 경쟁하는 곳을 따로 분석한다.

정해지면 이렇게 진행한다.
- 파일 이름은 **Area 그대로**에 조사일을 붙인다. 예: `구리눈NOON안과 반경5km(2026-10-08).md`, `구로구(2026-10-08).html`
- 저장 위치는 `C:\Users\thwan\OneDrive\Desktop\AFM 4th\week-5\quest\Reserch\` (폴더 철자 `Reserch` 그대로)
- 같은 이름 파일이 이미 있으면 덮어쓰기 전에 묻는다.
- 보고서에는 **두 가지를 모두** 담는다.
  1. **Area 안 업체 요약**: 분포, 비교표, 곳별 강점·약점, 전체 패턴
  2. **대상 업체 부정 리뷰 정리·분석**: 유형 집계, 원문 요약, 원인·비교·시기·대응 분석

## 1-B. 일반 모드: 주제·키워드 묻기

일반 텍스트로 한 번에 묻는다 (선택지가 뻔하지 않으므로 AskUserQuestion보다 자유 입력이 낫다).

```
리서치를 시작하기 전에 몇 가지만 알려주세요.
1. 주제: 무엇을 조사할까요? (예: 서울 구로구 안과)
2. 키워드: 꼭 넣을 검색어가 있나요? (예: 후기, 가격, 야간진료)
3. 범위·목적: 어디까지, 무엇에 쓰실 건가요? (예: 네이버 위주 / 부모님 백내장 병원 고르기)
4. 저장 폴더 이름: (없으면 제가 주제로 정합니다)
```

- 3·4번은 답이 없으면 상식선에서 정하고 결과에 적는다. 1·2번 답을 받기 전에는 탐색을 시작하지 않는다.
- 작업일은 오늘 날짜 `YYYY-MM-DD` 형식 (예: `Research(2026-10-06).md`).

## 2. 브라우저 MCP로 탐색 (최소 3곳)

### 사이트 고르기

주제에 맞게 **성격이 다른 출처를 3곳 이상** 섞는다. 같은 사이트의 다른 페이지는 1곳으로 센다.

| 주제 유형 | 추천 출처 조합 |
|---|---|
| 지역 업체·병원·맛집 | 네이버 통합검색 · 네이버 플레이스(목록+방문자 리뷰) · 네이버 블로그 · (카카오맵/굿닥/하이닥 등) |
| 제품·서비스 비교 | 공식 사이트 · 쇼핑/가격 비교 · 블로그/커뮤니티 후기 |
| 기술·도구 | 공식 문서 · GitHub · 최신 뉴스/블로그 |
| 정책·제도 | 정부·기관 공식 페이지 · 뉴스 · 해설 블로그 |

### 수집 요령 (검증된 방법)

- **텍스트는 스냅샷 대신 `browser_evaluate`로 뽑는다.** `() => document.body.innerText.slice(0, 8000)` 이 빠르고 토큰도 적다.
- **여러 검색어는 한 번에 돌린다.** 같은 도메인 페이지에 있는 상태에서 실행한다. 다른 도메인은 먼저 그 도메인으로 `browser_navigate` 한다.
  - 페이지 HTML에 데이터가 있으면 `fetch(url)` 와 `Promise.all` 로 동시에 가져온다. 가장 빠르다.
  - 화면을 그려야 하는 페이지(리뷰 펼치기 등)는 **같은 도메인 iframe** 에 띄워 `f.contentDocument` 를 조작한다.
  - `window.open` 으로 탭을 여러 개 여는 방식은 탭이 20개 정도가 되면 "Target page closed" 오류가 났다. 쓰지 않는다.
  - evaluate 호출 사이에는 변수가 사라진다. 다음 호출에서 쓸 함수와 결과는 `window.__xxx` 에 둔다.
  - 큰 결과는 `filename` 으로 `.playwright-mcp/*.json` 에 저장하고 `node -e` 로 가공한다. 이 PC에는 python이 없다.
- **목록이 스크롤로 더 나오는 페이지**는 스크롤 가능한 div를 찾아 `scrollTop = 1e6` 을 여러 번 주고 기다린다.
- **"펼쳐서 더보기" 버튼**이 있으면 버튼이 사라질 때까지 반복 클릭한다 (리뷰 수백 건 수집 가능).
- **네이버 플레이스** (`pcmap.place.naver.com/<업종>/list?query=...`):
  - 업체 ID·주소·전화·리뷰 수는 `window.__APOLLO_STATE__` 에 있다. 링크 href에는 ID가 없다.
  - 목록의 "리뷰 N" = 방문자 리뷰 + 블로그 리뷰 합계.
  - 방문자 리뷰: `/<업종>/<ID>/review/visitor`. **병원은 의료법상 "이런 점이 좋았어요" 키워드 통계가 없다** → 리뷰 원문을 직접 읽어 요약한다.
  - 지역 검색은 지도 중심 때문에 인접 지역 결과가 섞인다. 주소로 필터링하고, 동(洞) 단위 검색을 추가로 돌려 빠진 곳을 채운다.
  - **반경 N km** 는 목록 URL에 `&x=<경도>&y=<위도>` 를 붙여 검색하고, 좌표로 직선거리를 계산해 거른다. 검색어를 추가해도 새로 나오는 곳이 없을 때까지 늘린다.
  - 리뷰 앞의 **방문 태그**(예약 여부, 대기 시간 "바로 입장~2시간 이상")로 대기 분포를 숫자로 낼 수 있다.
  - 리뷰 페이지를 iframe으로 긁으면 중첩 `li` 때문에 **같은 리뷰가 두 번** 잡힌다. 날짜와 본문 앞부분으로 중복을 제거한다.
  - 업체 홈(`/<ID>/home`)에는 요일별 진료시간, 전문의 수, 편의시설, 조기마감 공지가 있다.
- **카카오맵**: 네이버 병원 리뷰에는 별점이 없으므로 카카오에서 **별점 분포**와 1~2점 후기 원문을 얻는다. 화면 스크롤 대신 **후기 JSON 주소**(`/places/tab/reviews/kakaomap/<ID>`)로 전체를 받는다([references/naver-place-scripts.md](references/naver-place-scripts.md) §7-1).
  - 네이버 최근 리뷰는 수술·시술 직후 만족 후기가 대부분이다. 장기 결과 불만은 카카오 저평점에 주로 있으니 두 플랫폼을 같이 본다.
- **Area가 시 전체처럼 크면** 구 × 업종 검색어 → 역·동 검색어로 목록을 채우고, 상위 업체는 최근 표본만 본다(§7-2).
- **네이버 블로그 검색**: `search.naver.com/search.naver?ssc=tab.blog.all&query=...` → `a[href*="blog.naver.com"]` 에서 제목·URL·요약을 뽑는다. 무관한 글(스팸·광고)은 버린다.
- **광고·체험단 구분**: "광고" 표시, 같은 해시태그 묶음 반복, 병원 정보 블록 포함 글은 마케팅일 가능성이 높다고 보고서에 표시한다.
- **부정/긍정 분석**이 필요하면 키워드 정규식으로 1차 필터한 뒤 **반드시 직접 읽고 다시 분류**한다(예: "기다렸지만 만족"은 부정이 아니다).
  - 분류는 "뚜렷한 부정 / 불만 섞인 긍정 / 제외" 세 가지로 나누고, 전체 대비 비율을 함께 적는다.
  - 정규식과 유형 목록은 [references/area-report.md](references/area-report.md)에 있다.
- **리뷰 몰림 패턴을 확인한다.** 월별 리뷰 수, 대기 태그 없는 한두 문장 긍정 리뷰가 몰린 달, 카카오 5점이 몰린 주를 본다.
  - 발견하면 "부탁받아 썼는지는 확인 못 함"과 함께 보고서에 적는다.
  - 주변 업체 표본이 짧은 기간에 몰려 있으면 부정 비율이 낮게 나올 수 있다는 점도 적는다.

### 탐색 중 지킬 것

- 수치(리뷰 수, 가격, 시간)는 **조사 시점 기준**임을 기록한다. 오래된 블로그의 정보는 날짜와 함께 적는다.
- 개인 이름(직원, 리뷰어 닉네임)은 보고서에 넣지 않는다. 원문에 있는 마스킹(성××)은 그대로 둔다.
- 로그인·결제·개인정보 입력이 필요한 페이지는 들어가지 않는다.

## 3. `.md` 작성

저장 위치는 모드에 따라 다르다.
- A 모드: `week-5/quest/Reserch/{Area}(YYYY-MM-DD).md`
- B 모드: `week-N/quest/<주제-슬러그>/Research(YYYY-MM-DD).md` (현재 주차 폴더. 메모리 `quest-output-location` 참고)

같은 이름의 파일이 이미 있으면 덮어쓰기 전에 사용자에게 묻는다.

**A 모드는 [references/area-report.md](references/area-report.md)의 틀을 쓴다.** 구성은 Area 요약 → 대상 업체 부정 리뷰 분석 ①~⑥ → 결론이다. 아래 템플릿은 B 모드용이다.

### 템플릿 (B 모드)

````markdown
# {주제} 리서치

- 조사일: {YYYY-MM-DD}
- 조사 도구: Playwright 브라우저로 {사이트1} · {사이트2} · {사이트3} 직접 수집
- 검색어: `{키워드1}`, `{키워드2}`, ...
- 범위·목적: {사용자가 말한 범위 / 목적}

> ⚠️ {한계 — 수치는 조사 시점 기준, 광고·체험단 가능성, 확인 못 한 것}

## 1. 한눈에 보기
{핵심 결론 3~5줄 또는 요약 표}

## 2. {본문 — 목록/비교 표}
| 항목 | ... | 출처 |

## 3. {항목별 상세 — 강점 / 약점 / 참고}

## 4. {목적별 추천 또는 결론}
| 목적 | 후보 | 근거 |

## 5. 참고한 글 목록
- [제목](URL)

## 6. 출처
- {사이트} 검색: URL
````

작성 규칙:

- **모든 주장에 근거를 단다.** 표에는 출처 열이나 링크, 상세에는 원문 인용 또는 링크.
- 추천은 "리뷰 기반 정리"임을 밝히고 단정하지 않는다.
- 확인하지 못한 것은 "확인 못 함"이라고 적는다. 지어내지 않는다.
- 다 쓴 뒤 **숫자를 다시 맞춰 본다**. 예: 지역별 업체 수의 합이 전체와 같은지, 유형별 건수가 원문 표와 맞는지, 중앙값 계산. 지난번에 "구리 7·중랑 10"으로 잘못 적어 나중에 고쳤다.

## 4. `.html` 웹페이지

`.md`와 **같은 폴더, 같은 파일명**(확장자만 `.html`). 외부 빌드 없이 파일 하나로 만든다.

### 구성

- 헤더: 제목, 조사일, 출처 요약, 한계 안내 박스
- 요약 카드 3~4개 (핵심 수치)
- 메인 표: 필터 칩(지역·유형 등) + 열 정렬 + 수치는 막대로
- 항목별 상세: `<details>` 접기, 좋은 점(초록)/아쉬운 점(빨강)/참고(회색)
- 결론·추천 카드, 참고 글 목록, 출처
- A 모드 구성(목차 칩, 비교표의 지역·일요일·야간 필터, 곳별 `<details>`, 부정 리뷰 필터 카드)은 [references/area-report.md](references/area-report.md) §5를 따른다.

### 스타일 규칙

- 색은 `:root` CSS 변수로 정의하고 `@media (prefers-color-scheme: dark)` 를 `:root:not([data-theme="light"])` 로 감싼다 + `:root[data-theme="dark"]` 도 정의 → 다크 모드와 테마 전환 버튼 지원
- 폰트: Google Fonts `Noto Sans KR`. 외부 스크립트가 필요하면 cdnjs/jsdelivr만.
- 모바일: 좌우 여백 16px, 넓은 표는 `overflow-x:auto` 래퍼, 가로 스크롤 없게.
- 데이터는 `<script>` 안 JS 배열로 두고 렌더링한다 (나중에 항목 추가가 쉽다). 사용자 입력이 아니어도 `esc()`로 이스케이프한다.
- `localStorage`는 테마 기억 정도만, try/catch로 감싼다.

### 검증 (생략 금지)

Playwright는 `file://` 접근이 막혀 있다. 로컬 서버로 띄워 확인한다.

```bash
cd "<폴더>" && npx -y http-server -p 5517 -s     # run_in_background
```

1. `http://localhost:5517/<파일명>.html?v=1` 로 연다.
   - 파일명의 괄호는 `%28` `%29` 로, 한글과 공백도 퍼센트 인코딩한다.
   - 수정 후 다시 볼 때는 `?v=` 값을 바꿔 캐시를 피한다.
   - 서버를 띄우자마자 열면 `ERR_CONNECTION_REFUSED` 가 날 수 있다. 3초 기다린 뒤 다시 연다.
2. `browser_console_messages` 로 에러 확인 (favicon 404는 무시).
3. 전체 스크린샷을 `.playwright-mcp/` 아래에 저장하고 Read로 직접 본다. 스크린샷 저장 경로는 프로젝트 폴더 안이어야 한다.
4. `browser_resize` 390×844 → `document.documentElement.scrollWidth > innerWidth` 가 false인지 확인 → 1280으로 되돌린다.
   - true면 화면 밖으로 나간 요소를 evaluate로 찾는다. 흔한 원인은 grid 카드 안의 넓은 표가 카드를 밀어내는 것이고, 카드에 `min-width:0` 을 주면 해결된다(2026-10-08 연세항정외과 리서치에서 발생).
5. 필터·정렬을 한 번씩 눌러 결과 건수와 **정렬 1위가 맞는지** evaluate로 확인한다. 데이터 배열에 없는 필드로 정렬하면 오류 없이 정렬만 안 된다(서울 안과에서 `nNeg` 필드가 없어 발생).
6. 서버 종료: TaskStop 후에도 node가 남으면
   `Get-NetTCPConnection -LocalPort 5517 -State Listen | % { Stop-Process -Id $_.OwningProcess -Force }`
7. `Start-Process "<html 경로>"` 로 사용자 기본 브라우저에 연다.
